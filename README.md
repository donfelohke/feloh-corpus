# FELOH Sovereign Corpus

**Canonical principle:** ONE CORPUS → MANY VIEWS → ONE PRACTICE.

The FELOH corpus is the source of record for the ecosystem's shared terminology, architecture, governance, decisions, specifications, provenance, and implementation status. Specialist repositories may contain their own implementations and working material, but they should link back to this corpus rather than create conflicting definitions of the same canon.

## Canonical relationships

- **FELOH / DonFeloh** — human authorship, generation, and expression.
- **NAKEBUSEN** — beauty craft, livelihood, customer relationships, and the ecosystem's transaction boundary.
- **WARENA** — reproducible and maintainable computing, infrastructure, and local-first systems.
- **IKAI** — reflexive-compute research; a mirror, not a judge.
- **GENJE / GENJE ZA WARENA** — Genge, livecoding, movement, and choreohacking.

**Governing rule: ONLY NAKEBUSEN TRANSACTS.**

## Evidence and status discipline

Use explicit status labels where applicable:

- `LIVE`
- `PROTOTYPE`
- `RESEARCH`
- `CONCEPT`
- `HISTORICAL`
- `SUPERSEDED`
- `UNKNOWN`

A claim is not an implementation. A specification is not proof of execution. A commit proves that content was committed; it does not by itself prove that the described behaviour works.

Use the evidence chain:

`CLAIM → DOCUMENT → IMPLEMENTATION → OBSERVATION → RECORD → ATTESTATION → SEQ-07`

Record the relevant source, decision, version or commit, observed result, and any superseding decision. Mark unverified controls and behaviours as `UNKNOWN` or `NOT VERIFIED`, rather than implying success.

## Stewardship

The corpus is intended to support distributed stewardship, contributor onboarding, and succession rather than permanent founder control. Changes should preserve human authorship, decision provenance, customer privacy, and reversible review where practical.

Use focused branches and pull requests for substantive changes. Do not commit credentials, secrets, or private customer records. IKAI must not be represented as a face-identification, diagnosis, scoring, covert-surveillance, or hidden-profiling system.

## Current maturity

This README establishes the repository's purpose and shared terminology. It does **not** assert that branch protections, security scanning, automated validation, a formal council, or successor assignments are configured. Verify those independently and record evidence before marking them active.
