## Technology routing

WARENA owns technical implementation and policy. The current shared baseline is native-first, libre-first and local-first, with JavaScript and web technologies excluded as WARENA/IKAI application/runtime architecture. Static documentation/publication is distinct from a native system runtime.

Desktop research is X11-first: X.Org initial compatibility, XLibre compatibility experiment, Gershwin case study, Guile-WM / WM-NG research; Wayland/dwl-guile is secondary/experimental and Sway is a comparison/recovery baseline. See [Technology Constitution](technology-policy-2026-11-17.md) and WARENA's specialist desktop records.

## Routing rules

1. Put shared definitions and cross-domain policy in the FELOH Corpus.
2. Put service facts and operational beauty procedures in NAKEBUSEN.
3. Put technical source, configuration and reproducibility evidence in WARENA.
4. Put IKAI protocols, experiments and privacy decisions in IKAI.
5. Put creative source, movement records and attribution in GENJE.
6. Put asset provenance and rights in Gallery; file presence is not publication permission.
7. Put rendered public copy, accessibility results and deployment evidence in the website repository.
8. Do not duplicate large canonical documents; link to the source of record.
9. Do not store private client records, secrets, credentials or payment references in public repositories.
10. Mark unknown ownership, status or evidence as UNKNOWN; do not guess.

## Cross-domain work record

For work spanning domains, record the question, expected outcome, lead and affected domains, canonical sources reviewed, dependencies, assumptions, evidence, unresolved questions, repositories/files changed, tests, approval state and next action.

## Maintenance

When a shared relationship changes, update the Master Corpus first and then align dependent views. Specialist records remain authoritative for their implementation details. A document or merge does not certify operational maturity.
