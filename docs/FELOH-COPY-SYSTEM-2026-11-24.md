## 3. Voice and editorial principles

The voice is grounded, assured, warm, culturally conscious, curious, disciplined, technically literate and human.

1. Lead with the person's need, the work or the evidence—not abstract claims of greatness.
2. Prefer concrete verbs and plain language.
3. Use African cultural references with context, attribution and respect.
4. Keep cultural identity contemporary; do not turn it into decorative shorthand.
5. Explain technical terms when addressing a general audience; retain precise terminology in engineering records.
6. Distinguish founder interpretation from independently verified linguistic or historical evidence.
7. Never invent testimonials, qualifications, clients, partnerships, metrics, guarantees or availability.
8. A research note is not a prototype; a prototype is not a released product.
9. A repository file is not proof of a deployed service.
10. Keep the human author and decision-maker visible.

Avoid generic luxury language, empty innovation claims, forced slang, ungrounded Afro-futurist tropes, default Rasta shorthand, neon-AI haze, beauty scoring and surveillance metaphors.

## 5. Design copy

The visual language is editorial African-rooted design with restrained dark-terminal depth. It should feel crafted, legible, materially grounded and technically literate.

- Hierarchy before ornament.
- Typography before decorative graphics.
- Human presence and the work before abstract interface effects.
- Negative space used deliberately.
- Colour used semantically, with accessible contrast.
- Documentary evidence over generic stock imagery.
- Motion only where it communicates a real relationship or process.
- Reusable components with consistent names, states and responsive behaviour.

Use the approved forest, ivory, near-black, sage, ochre/gold and terracotta family. Cormorant Garamond is the editorial display reference, Inter the body/interface reference and JetBrains Mono the technical metadata reference. Confirm actual font licensing, loading and availability before implementation.

Avoid generic luxury templates, default Rasta colour shorthand, decorative motifs without context, gratuitous glitch, neon-purple AI aesthetics, visual clutter and unreadable type.

Use explicit labels such as **ROOT / CAPABILITY / MIRROR / EXPRESSION**, **LIVE / RESEARCH / CONCEPT**, and **ENQUIRY / AGREED / CONFIRMED** only where the underlying state is real. Do not style a proposal as a verified status.

## 7. Technical copy

Technical writing must identify the problem and intended user; system boundary and ownership; architecture and interfaces; dependencies, versions and source revisions; target hardware and environment; constraints, threat model and privacy boundary; test method, result and evidence location; limitations, unresolved risks and rollback/recovery; and maturity/publication status.

Use maturity labels consistently: **CONCEPT, RESEARCH, DOCUMENTED, CONFIGURED, BUILT, TESTED, VALIDATED, DEPLOYED, PRODUCTION-VERIFIED, UNKNOWN, BLOCKED, SUPERSEDED**. Do not collapse them into a single badge or adjective.

Preferred technical description: "This repository documents and develops..." Use "supports" only where a capability is demonstrated. Use "deployed" only with a deployment record. Use "production-ready" only with defined acceptance criteria and operational evidence.
