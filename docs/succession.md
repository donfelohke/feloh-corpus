# Stewardship and Succession

## Objective

The corpus should remain understandable, maintainable, and useful beyond the availability of any single founder or contributor. Succession is a practice of transferring context and authority, not merely handing over credentials.

## Principles

- Preserve human authorship and credit.
- Make important decisions discoverable and explain their rationale.
- Separate roles and responsibilities from personal identity where practical.
- Use least-privilege access and individually attributable accounts.
- Keep recovery procedures documented without publishing secrets.
- Encourage multiple people to understand critical workflows.
- Do not describe a distributed process as active until participants, permissions, and operating procedures are verified.

## Stewardship areas

A future stewardship register should identify, for each area:

| Area | Required continuity information |
|---|---|
| Canon and editorial direction | Source of record, accepted terminology, review process, unresolved conflicts |
| Repository operations | Maintainers, branch model, review rules, backup and recovery procedure |
| WARENA systems | Hardware/software inventory, reproducible setup, dependencies, recovery tests |
| NAKEBUSEN operations | Approved service catalogue, transaction boundary, customer privacy, operational handover |
| IKAI research | Research status, privacy constraints, consent model, data lifecycle, evaluation evidence |
| GENJE practice | Creative source files, performance setup, licensing, attribution, workshop materials |
| Public views and websites | Build/deploy path, domain ownership, accessibility, offline fallback |

This table is a planning structure; it does not assert that named successors or backup operators have been appointed.

## Handover checklist

- [ ] Identify the canonical source and current revision.
- [ ] Inventory repositories, domains, hardware, services, and external dependencies.
- [ ] Identify owners and backup stewards for each critical area.
- [ ] Verify access using individually attributable accounts and least privilege.
- [ ] Document recovery steps and test them without exposing secrets.
- [ ] Record open decisions, unresolved conflicts, and known failure modes.
- [ ] Confirm licenses, provenance, and attribution for critical assets.
- [ ] Run a practical handover exercise with a second contributor.
- [ ] Record evidence and date of the exercise.
- [ ] Review access after role changes and revoke access that is no longer required.

## Access and safety

Do not place passwords, private keys, recovery codes, customer records, or sensitive personal data in this repository. Store secrets in an appropriate access-controlled system and document only the recovery process and responsible role.
