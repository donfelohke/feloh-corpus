## 1. Executive finding

The portfolio has a coherent domain architecture and explicit maturity, privacy and provenance rules. The principal risk is documentation drift: repeated public claims have been copied into separate READMEs, campaign briefs, service catalogues and website copy, where names, status labels and details diverge.

Evidence labels:
- **VERIFIED IN REPOSITORY** — directly observed in the named GitHub source at review time.
- **OWNER-APPROVED CANON** — decision recorded in the current portfolio decision or implementation brief.
- **UNVERIFIED EXTERNALLY** — requires an independent operational, rights, identity, payment or browser check.
- **PROPOSAL** — recommended future state, not a new fact or authorization.

A repository document proves what the repository says. It does not prove current service availability, working payment routing, image rights, participant consent, software deployment, or live website accessibility.

## 6. Evidence classes and minimum proof

Use these labels consistently:
- **VERIFIED** — source and method identified; verification can be repeated.
- **CORROBORATED** — multiple independent sources, not directly established.
- **OWNER-APPROVED** — explicit owner decision; not necessarily external verification.
- **UNVERIFIED** — no adequate evidence yet.
- **DISPUTED** — sources conflict.
- **INTERPRETATION** — authored meaning, not a factual or etymological assertion.
- **PROPOSAL** — suggested future state.
- **HISTORICAL** — true only for a prior period or superseded state.

Maturity is a separate axis: LIVE, PROTOTYPE, RESEARCH, CONCEPT, HISTORICAL, SUPERSEDED, UNKNOWN.

Minimum proof:
- **Service / price:** dated owner approval, scope, current location, starting-price conditions and enquiry route.
- **Payment:** verified recipient/merchant, instrument identifier, authoritative confirmation and fraud-safe customer instructions.
- **Founder title / credentials:** explicit approval plus suitable evidence; otherwise omit.
- **Social account:** destination opens, identity confirmed, role and monitoring responsibility known.
- **Image:** original binary, source/creator, rights/licence or permission, consent where relevant, intended use and review record.
- **Software deployment:** named host, resolved configuration, version/channel evidence, date, operational observation and recovery evidence.
- **Website release:** merged commit, successful Pages deployment, live URL response, browser inspection, interaction tests and accessibility review.

## 7. Website release gates

Do not describe the website as verified, launched, accessible or production-ready solely because source files exist or a workflow is green.

1. Resolve copy against current canon and public-facts register.
2. Resolve disputed owner facts: payment, role, location, languages and channels.
3. Correct service labels and canonical lockup.
4. Run HTML and JavaScript checks; record results and tool versions.
5. Test keyboard navigation, visible focus, semantic headings, labels, contrast, reduced motion and text resizing.
6. Test language/theme controls, navigation, telephone, WhatsApp, email and outbound links.
7. Inspect widths 320, 360, 390, 430, 760, 1024 px and desktop.
8. Merge only after review; confirm Pages deployment and inspect public URL.
9. Record commit, workflow run, URL, browser/device, date and known limitations.
