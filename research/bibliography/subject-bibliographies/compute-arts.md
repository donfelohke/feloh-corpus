## Annotation policy

A URL being reachable is not full-text review. Each entry records the review depth and the claims it can support. For formal publication, capture author/editor, exact title, date/version, access date, relevant sections/pages and persistent identifier. Check legal material against current authoritative Kenyan sources before making a legal determination.

## D. Data stewardship and software preservation

### CA-009 — Wilkinson, M. D. et al., “The FAIR Guiding Principles for scientific data management and stewardship,” Scientific Data 3, 160018 (2016)
- Type: Peer-reviewed open-access article.
- DOI: https://doi.org/10.1038/sdata.2016.18
- Review status: Abstract/page description reviewed; full-paper review still required for formal synthesis.
- Annotation: FAIR concerns findability, accessibility, interoperability and reusability of research objects, including data, algorithms and workflows; provenance and licensing matter.
- Use: Evaluate whether creative research artefacts can be found, interpreted and reused responsibly.
- Limitation: FAIR is not equivalent to open access, ethical permission or unrestricted reuse. Restricted access may be appropriate for sensitive material.

### CA-010 — Software Heritage, “Software is our heritage”
- Type: Public software preservation infrastructure.
- URL: https://www.softwareheritage.org/
- Review status: Official service description reviewed.
- Annotation: Describes preservation of source code and development history for long-term access.
- Use: Consider source-code preservation alongside local Git, exports, checksums and backups.
- Limitation: Archiving does not establish licence permission, dependency availability or successful builds.

### CA-011 — Software Heritage FAQ
- Type: Official service documentation.
- URL: https://www.softwareheritage.org/software-heritage-faq/
- Review status: Official FAQ reviewed.
- Annotation: Distinguishes source preservation from permission to reuse; users must determine applicable rights and licences.
- Use: Include licence review and dependency preservation in the software checklist.
- Limitation: Not legal advice and not proof that any particular repository has been archived.

### CA-012 — GNU Project, GNU Guix Reference Manual
- Type: Official technical manual.
- URL: https://guix.gnu.org/manual/en/guix.pdf
- Review status: Manual excerpt reviewed; relevant sections/version must be pinned during implementation.
- Annotation: Documents build isolation and mechanisms intended to support reproducible builds.
- Use: Evaluate Guix/RDE for recording creative software dependencies and rebuildable environments.
- Limitation: Design intent is not proof that a particular project builds reproducibly. Record system, channels/commits, inputs, build result and independent reproduction.

## E. Kenyan cultural rights and copyright

- URL: https://www.wipo.int/wipolex/en/legislation/details/21462

## Synthesis for FELOH

1. Use existing livecoding software as a testable baseline, not a predetermined creative solution.
2. Treat source, environment and rights metadata as part of the artefact.
3. Preserve originals and link derivatives instead of silently overwriting.
4. Separate technical reproducibility from artistic equivalence.
5. Separate public discoverability from permission to reuse.
6. Treat cultural consent, attribution and community protocols as design requirements, not metadata alone.
7. Treat movement descriptions as situated interpretations, not identity labels or clinical measurements.
8. Evaluate the human workflow as well as software execution.
